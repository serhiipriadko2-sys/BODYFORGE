# BODYFORGE: настраиваемый мобильный интерфейс

Инженерно-исследовательский отчёт, 26.10.2026. Локальная реализация; результаты проверок ниже имеют указанные границы. Это не опубликованное научное исследование и не сертификат доступности.

## Постановка задачи

Сделать существующее приложение визуально спокойнее, сохранить центрального трёхмерного человека и основной цикл тренировки, добавить выбор палитры и материала интерфейса. Источники направления — три предоставленных владельцем изображения: компактный игровой интерфейс с фиолетово-бирюзовым акцентом, редактор человеческого аватара и тёмное фитнес-приложение с лаймовым акцентом.

Из референсов перенесены иерархия, компактные карточки, центральный персонаж, плавающая навигация и контролируемый акцент. Показатели сна, пульса, калорий и шагов из изображений не превращены в фиктивные данные BODYFORGE. Текущая анатомическая 3D-модель остаётся реальным WebGL-объектом; новый стиль не подменяет её изображением.

## Вопросы и статус гипотез

1. Можно ли менять внешний вид, не затрагивая игровой профиль и результат тренировки? Это проверяемое инженерное требование: побайтовое сравнение игровых ключей до и после сценариев настройки.
2. Можно ли сохранить читаемость при произвольном акценте? Для заданных непрозрачных пар это проверяется расчётом WCAG и детерминированной выборкой RGB. Это не доказательство соответствия всей страницы WCAG.
3. Улучшит ли новая иерархия поиск главного действия? **Гипотеза.** Нужен пользовательский сценарий с наблюдением ошибок и времени поиска; участники в этой итерации не исследовались.
4. Достаточно ли дёшево стекло на Android? **Гипотеза.** Нужны измерения одного сценария на одном устройстве со стеклянным и матовым режимами. FPS, расход энергии и температура телефона не измерялись.

## Основания решений

Обычный текст требует контраста не ниже 4.5:1; крупный — 3:1. Важен итоговый фон за текстом, а не только номинальная палитра. Поэтому контентные карточки непрозрачны, а стеклянные элементы имеют плотную подложку. [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C: G18](https://www.w3.org/WAI/WCAG22/Techniques/general/G18).

Материал стекла подчёркивает управляющий слой: верхнюю и нижнюю навигацию, диалог настроек. Это веб-интерпретация направления Liquid Glass, а не реализация нативного материала Apple. Размывание не применяется к видеопотоку, скелету или каждому игровому блоку. [Apple: Materials](https://developer.apple.com/design/human-interface-guidelines/materials), [WebKit: Backdrop Filters](https://webkit.org/blog/3632/introducing-backdrop-filters/).

Палитра не должна быть единственным обозначением состояния. Выбранный вариант отмечен подписью, галочкой и `aria-pressed`; активная навигация имеет форму и подчёркивание. Ошибка и успех сохраняют смысл независимо от декоративного цвета. [W3C: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), [W3C: Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

Проектная цель для основных новых управляющих элементов — 44 CSS px. Это более строгая цель, чем минимум AA 24×24 с исключениями; отсутствие горизонтального переполнения проверяется отдельно. [W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), [W3C: Target Size Enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html), [W3C: Reflow](https://www.w3.org/WAI/WCAG21/Understanding/reflow).

Предусмотрены матовый режим, повышенный контраст, `prefers-reduced-transparency`, `prefers-reduced-motion` и полноценная непрозрачная поверхность при отсутствии `backdrop-filter`. Поддержка системного сигнала уменьшения прозрачности зависит от браузера; ручной матовый режим доступен независимо от него. [W3C: Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#user-preferences), [web.dev: Backdrop Filter](https://web.dev/articles/backdrop-filter).

## Реализация и воспроизводимость

| Слой | Реализация | Обоснование |
|---|---|---|
| Семантические цвета | `appearance.css`: фон, поверхность, текст, вторичный текст, акцент, текст на акценте, границы | Согласованное оформление разных экранов |
| Палитра | Мята, Медь, Неон, Лайм, пользовательский `#rrggbb` | Управляемые варианты без запрета собственного цвета |
| Контраст акцента | `appearance.ts`: относительная яркость sRGB, выбор чёрного/белого текста, отдельный осветлённый акцент для подписей | Тёмный пользовательский акцент не делает подписи невидимыми |
| Материал | Стекло / Матовый; повышенный контраст отключает прозрачность и blur | Читаемость и управляемая стоимость эффектов |
| Настройки | Native `<dialog>`, реальные radio/checkbox/input; Escape, modal focus | Использование браузерной семантики вместо самодельной ловушки фокуса |
| Хранение | Отдельный `bodyforge:appearance:v1`; валидация версии и полей; read-back; storage events | Оформление не переписывает профиль, backup, XP и журнал результатов |
| Ошибки | Понятное сообщение при неподтверждённой записи; текущая вкладка продолжает показывать выбранный стиль | Локальное отображение не выдаётся за сохранённую настройку |

Формула проверки: `contrast = (Lmax + 0.05) / (Lmin + 0.05)`, где относительная яркость вычисляется после преобразования sRGB по WCAG. Для обычного акцентного текста используется контрольная поверхность `#303847`, более светлая, чем основные контентные поверхности. В усиленном режиме целевое отношение этой пары — 7:1. Выбор чёрного/белого текста на произвольной цветной кнопке обеспечивает цель 4.5:1, но не гарантирует 7:1 для любого пользовательского цвета.

8192 проверяемые комбинации — сетка 16×16×16 RGB в двух режимах контраста. Такая выборка воспроизводима и включает крайние цвета; она не является исчерпывающим перебором 16 777 216 цветов и не имитирует человеческое зрение.

Первое открытие только читает настройки. Неизвестная версия или повреждённая запись не перезаписывается автоматически. Смена стиля обновляет интерфейс сразу, затем сообщает результат записи. Конкурентные изменения оформления используют последнее полученное значение; это предпочтения интерфейса, а не транзакция игровых наград. Сброс восстанавливает только оформление.

В финальной сборке основной JS — 363 384 байта; камера — отдельный chunk 154 276 байт. Большой lazy chunk 3D остаётся около 627.49 kB: предупреждение сборщика не скрыто, ускорение на устройстве из размера файла не выводится. Никакой новый рендерер, изображение или библиотека эффектов не добавлены.

Реальные дефекты, обнаруженные дополнительными проверками и исправленные до завершения:

- Правило стекла имело большую CSS-специфичность, чем системное уменьшение прозрачности. После исправления при подтверждённом `matchMedia=true` все три стеклянных элемента получают непрозрачный фон и `backdrop-filter: none`.
- Диалог на 320 px имел горизонтальное переполнение 1 px из-за минимального размера flex-содержимого. Устранено через `min-width: 0` и перенос текста, без маскирования `overflow-x: hidden`. Финальные clientWidth/scrollWidth — 280/280 px.
- Подсказка поворота персонажа пересекалась с показателем мышц. Прямоугольники не пересекаются на 320/360/390 px после изменения размещения.
- Декоративный hover-фильтр мог осветлить произвольную кнопку после расчёта контраста. Фильтр убран. Для граничного цвета `#747474` реальная кнопка при наведении сохраняет 4.674:1; проверка сравнивает неокруглённое значение с порогом.

Предварительные ошибки тестового harness также сохранены отдельно: недоступный CDP внутри sandbox, экранирование селектора, измерение цвета во время перехода, неверно подготовленный фокус открывающей кнопки, отсутствие ожидания загрузки GLB. Они не выданы за дефекты приложения. При проверке native dialog допускается браузерный промежуток без DOM-фокуса; фокус на интерактивный элемент фонового приложения отклоняется, Escape возвращает фокус исходной кнопке.

Команды: `npm test -- --maxWorkers=1 --no-file-parallelism`, `npm run build`, `npm run qa:appearance`, `npm run qa:mobile`, `npm run qa:tower20`, `npm run qa:privacy`, `git diff --check`. Браузерные проверки используют собственные временные профили Chrome и синтетические игровые данные; настоящая камера владельца и её видеозапись не используются.

Новый сценарий проверяет реальные две вкладки приложения, preset/custom цвета, ошибки чтения и записи, reload, передачу настройки через storage event, native Escape/Tab/focus, размеры контролов, переполнение и сохранность игровых строк. Численные проверки контраста ограничены явно перечисленными парами и фонами.

## Ограничения и следующий эксперимент

Не подтверждены: предпочтение пользователей, полное соответствие WCAG, системное увеличение текста/200% zoom, работа с каждым экранным диктором, настоящий браузер без поддержки `backdrop-filter`, реальная Android-производительность стекла и WebGL, физическая точность распознавания упражнений. Матовый fallback проверен в текущем Chrome; ветка отсутствия поддержки фильтра присутствует в CSS, но отдельный неподдерживающий браузер не запускался. Опциональные настройки оформления не получают гарантию сохранности при отключении питания. Цвета кожи, одежды и платформы внутри 3D-сцены не являются настройкой палитры интерфейса.

Следующий практический эксперимент: на реальном Android пройти один и тот же маршрут «открыть приложение → начать тренировку → завершить → изменить стиль» в матовом и стеклянном режиме. Сначала определить устройство, браузер, сценарий и сбор измерений, затем сравнивать время кадра/отклик и читаемость. Видео не записывать и не передавать без отдельного согласия. Условие пересмотра — потеря читаемости, недоступное действие, ошибка сохранения либо измеряемое ухудшение относительно матового режима.
