**Цель:** превратить существующую локальную фитнес-RPG в высококачественный мобильный продукт с авторским художественным стилем, достоверными игровыми результатами, долговечными сохранениями и содержательной игровой глубиной.

## 0. Резюме и ключевое решение

AAA — ориентир качества исполнения, а не обещание масштаба студии или фотореализма. Приоритет — законченный вертикальный срез: пользователь запускает тренировку, понимает правила камеры, получает корректно зафиксированный результат и ровно одну предусмотренную награду, видит развитие бойца, без риска потери данных выбирает следующую цель. Камера, 3D и хранение должны оставаться работоспособными независимо друг от друга.

Не переписывать проект на Unity, Unreal или другой стек ради ярлыка AAA. Сначала укрепить действующие React/TypeScript/Vite, MediaPipe и Three.js, затем расширять игру через проверяемые контракты. Нативный Android — отдельная поверхность одного продукта, не новый независимый игровой движок. Веб и Android имеют общий игровой домен, но разные возможности сенсоров.

Предлагаемый путь: **фиксируем базу → защищаем прогресс → подтверждаем распознавание → полируем мобильный UX и 3D → углубляем RPG → обеспечиваем автономность и перенос → готовим релиз → только затем исследуем социальную игру.** Внешние публикации, новый APK, новые разрешения, сервер и коммерциализация проходят отдельные гейты согласования. В текущем исследовании ничего из этого не выполнялось.

## 2. Продуктовая концепция: фитнес-RPG, а не калькулятор с героем

### 2.1 Три вложенных игровых цикла

**Микроцикл (секунды–минуты).** Выбрать действие → поставить телефон → получить сигнал готовности → выполнить добровольную цель → видеть честные подтверждения/причины отказа → закончить или остановиться. Краткий HUD: счёт, цель, состояние трекинга, таймер/отдых, стоп. Кадр важнее декора.

**Средний цикл (день–неделя).** Подтверждённый результат → сохранение → награда → выбор улучшения/косметики → одна из доступных миссий → план следующей сессии. Возвращение после паузы не обнуляет достижения. Не требовать каждый день тяжёлой нагрузки; дневные задачи опциональны. Прогресс отражает выполненные действия, а не недоказанную физиологию.

**Долгий цикл (недели–месяцы).** Освоение типов движений, сюжетные главы кузницы, коллекция снаряжения, испытания мастерства, визуальная эволюция бойца и личные рекорды. Цель — разнообразие и самовыражение, а не бесконечная инфляция уровня.

### 2.2 Принципы выбора механик

- Компетентность: игрок узнаёт причину неудачи, видит достижимую следующую цель. Автономия: можно поменять упражнение, темп, сложность, отдохнуть. Самовыражение: косметические решения различимы, не влияют на точность камеры.
- Достижение даётся за уже зафиксированное событие. Никакого бонуса за согласие на Health Connect, камеру, передачу данных или постоянную активность в приложении.
- Режимы имеют разный смысл: обучение/практика без заработка; обычная подтверждённая тренировка; испытание; будущая программа из нескольких упражнений. Отказ от камеры даёт режим просмотра/личного ручного дневника без поддельного «проверенного» результата.
- Любые планы физических занятий — общие для здоровых взрослых, опциональные, не диагноз и не персональная лечебная программа. При боли, головокружении или плохом самочувствии — прекратить. Не требовать тренировок ради «серии», не оценивать тело по внешнему виду. Для иной аудитории — отдельная экспертиза и адаптация.
- Не переносить результаты исследований на BODYFORGE автоматически. Метаанализ 36 испытаний геймификации показал небольшое среднее преимущество по активности [S7]; полезность именно нашей экономики — гипотеза. Позиция ACSM 2026 [S8] подтверждает пользу прогрессивного силового тренинга для здоровых взрослых, но не превращает 20 повторов с камерой в универсальную норму.

### 3.2 AURORA FORGE — art bible (PROPOSED)

- Визуальный язык: антрацит, сине-стальные панели, холодный свет, матовые поверхности, контрастные контуры. Cyan — действие/навигация, lime — достигнутый игровой прогресс, violet — косметика, amber — осторожность. Не использовать красный как стыд. Состояния кодируются также текстом/иконкой.
- Сохранить существующие theme tokens (`appearance.css`, `neonPulseV2.css`, `trainingExperience.css`), high contrast и reduced motion. Перед новой палитрой составить карту реальных значений и контрастов. Не вводить отдельную несогласованную CSS-систему.
- Плотность: один визуальный акцент на карточку, короткие подписи; раскрытия для редких настроек. 8/12/16/24 px ритм как исходная гипотеза, не принудительный редизайн всего экрана. При 320 px главный CTA и нижний dock не перекрываются; минимум 44 CSS px для основных целей касания (проектная норма), Android 48 dp. WCAG 2.2 AA — внешний критерий, не автоматическая сертификация [S13].
- Типографика: отличать заголовки, значимые числа и пояснения; сохранить кириллицу, локальные шрифты и fallback. Числа с tabular-nums. Не обрезать локализованный текст. Проверять 200% масштаб, 320px reflow, safe-area, landscape и screen reader.
- Анимации: 120–250 ms как начальная настройка, качественная короткая кузнечная «закалка» после durable save; статичная альтернатива. Звуки — отдельные сигналы готовности, зачёта, завершения и ошибки, отключаемые. Haptic только если доступно, никогда единственный сигнал. Запрет опасного мигания.

## 4. Камера и научная валидация движений

### 4.1 Целевая архитектура (не большой rewrite)

Текущие модули `camera.ts`, `frameLoop.ts`, `exerciseFraming.ts`, `poseGuidance.ts`, `squatCounter.ts`, `exerciseCounter.ts`, App refs — база. Выделять только проверяемые границы, по одному seam за патч:

```text
User intent / exercise definition
  -> permission & camera acquisition (session generation, abort)
  -> frame gate (fresh, monotonic timestamp, bounded queue)
  -> PoseLandmarker adapter (model/version/capability)
  -> tracking + framing + normalized features
  -> pure exercise FSM (candidate -> accepted / rejected / unknown)
  -> completion validator (typed target, matching session)
  -> durable receipt -> reward transaction -> read-back
  -> UI feedback and optional local diagnostics
```

Инварианты: не запрашивать камеру заранее; одна активная сессия и один владелец stream; late stream stop, отмена и уничтожение идемпотентны; stale callback не может изменить новую сессию; один кадр обрабатывается не более раза; monotonic время, не Date.now для длительности; неизвестная поза не становится «0» или подтверждением; при loss/смене камеры не засчитывать незавершённый цикл; таймер не включает невалидные интервалы. Действующая планка: 30 секунд непрерывного удержания; поведение краткой потери видимости уточнить по текущему коду и закрепить тестом, не придумывать. Успех финиша только после записанного результата; stop до цели не выдаёт награду.

Предложение для интерфейса (адаптировать существующий контракт, а не создавать дубли): `PoseObservation {sessionId, frameId, monotonicMs, landmarks, visibility, frameAspect, modelVersion}` — transient, не сохранять; `CounterEvent {sessionId, seq, exerciseId, phase, accepted, qualityReason, timestamp}`; `WorkoutReceipt {id, sessionId, schemaVersion, exerciseId, mode, target, completedUnits, unit, startedAt, finishedAt, activeMs, completionReason, validatorVersion, rewardPolicyVersion, provenance}`. В receipt не включать landmarks или camera device ID. Порог/модель — версия алгоритма, не медицинский сертификат.

### 4.3 Исследовательский протокол: не путать синтетические тесты и человека

**Гипотезы:** H-CV1 — улучшенное качество кадра уменьшает ложные зачёты относительно baseline; H-CV2 — устойчивые фазы и hysteresis уменьшают дубли; H-CV3 — worker/ограничение частоты улучшает UI без значимого ухудшения распознавания. Сначала заморозить baseline алгоритма и определить рабочий диапазон. Доступные исследования markerless motion capture показывают вариабельность точности по движению, плоскости и суставу [S3]; они не валидируют наш алгоритм.

**Единица наблюдения:** сессия участника × упражнение × устройство × заранее заданное условие. Не считать тысячи соседних кадров независимыми наблюдениями. Разделять development/tuning и holdout по участникам; избегать утечки одних и тех же людей между наборами, фиксировать версии модели и пороги до финального теста. Если выполняется ретюнинг после holdout, это новый цикл с новым holdout.

**Набор условий:** 320–428 и landscape; минимум три класса Android (слабый/средний/быстрый), различные размеры кадра, WebView и Chrome отдельно; Safari/iOS только если заявляется поддержка. Освещение/контраст, дистанция, ракурс, одежда, разные антропометрические пропорции; корректные медленные и обычные повторения; безопасные неполные движения, отсутствие движения, краткая потеря видимости, пропуски кадров. Не просить участников выполнять опасные движения, доводить себя до отказа или ускоряться для QA. Паузы, добровольное согласие, возможность остановиться. Первичный пилот 12–20 совершеннолетних добровольцев по возможности и этическому согласованию, с распределённым дизайном вместо выполнения всего на каждом человеке. Это поиск проблем, не достаточная статистическая мощность. Для confirmatory набора рассчитать объём по наблюдаемой межсессионной вариативности и требуемой ширине доверительного интервала; не обещать N заранее без этих параметров. Не включать медицинские данные в разработческие логи.

**Референс:** два независимых обученных наблюдателя размечают допустимые завершённые движения и интервалы по общей инструкции; разногласия adjudication третьим или консенсусом до сравнения с алгоритмом. По умолчанию без записи видео: ручной счёт/временные метки, отдельно согласованная запись только если необходима, локально, ограниченный срок, удалить по протоколу. В случае недостаточного согласия маркировать ambiguous, не подгонять под алгоритм; отдельно показывать долю исключений. Для планки — согласованные интервалы начала/конца, не просто число секунд приложения.

**Метрики:** сопоставить подтверждённые события с референсом один-к-одному в заранее выбранном допуске по времени; оптимизировать matching без двойного совпадения. TP — верный зачёт, FP — ложный/лишний, FN — пропущенный. Precision = TP/(TP+FP), Recall = TP/(TP+FN), F1 = 2PR/(P+R). При пустом знаменателе NA. Отдельно false reps/min в сценариях покоя/неполного движения, MAE количества по сессиям, систематическая ошибка и разброс, доля ошибочных финишей, доля отмен из-за трекинга, tracking coverage, latency p50/p95. Для времени планки абсолютная ошибка удержания и ложный финиш. Не скрывать abstain и не выдавать высокую precision за высокую полезность при низком recall. Для доверительных интервалов — bootstrap на уровне участников (либо согласованная кластерная модель), отчёт по упражнениям и устройствам, число людей/сессий/событий и пропуски. Не агрегировать в одно «accuracy 99%».

**Предварительные гейты TARGET, утверждаются после пилота:** 0 ложных финишей и двойных выплат во всех автоматизированных критических сценариях; в полевой подтверждающей выборке ноль наблюдавшихся ложных финишей с явным интервалом неопределённости (ноль наблюдений не равен нулевому риску); ориентир precision ≥0,95 и recall ≥0,90 по поддерживаемому режиму, нижние доверительные границы и worst-stratum заранее согласовать; MAE ≤1 повтор на стандартную 20-rep сессию как проектный ориентир, для планки ≤1 s ошибки времени в валидном кадре; доля неопределённых/неподдерживаемых случаев ограничивается отдельным гейтом, определяемым пилотом. Не ослаблять цели после просмотра данных ради PASS. Если не достигнуты, сохранить EXPERIMENTAL, ограничить условия или режим. Игровая награда за локальный результат не становится медицинской оценкой/серверным доказательством.

### 4.4 Технические эксперименты производительности CV

Google документирует синхронность `detectForVideo` и рекомендует вынести вычисление с UI-потока [S1]. Это основание для spike, не гарантия совместимости. A/B на одной модели и одинаковых последовательностях: текущий main-thread baseline vs Worker с одним кадром in-flight и передачей `ImageBitmap`/`VideoFrame` при поддержке, закрытием ресурсов, bounded queue, last-frame drop и abort. Проверить fallback Safari/WebView, загрузку WASM, GPU/CPU делегаты, память и время первого кадра. Сравнивать precision/recall/finish, long tasks, p95 UI latency, inference cadence, тепловой троттлинг. Не считать FPS камеры, inference FPS и render FPS одним числом. Нет преимущества или ухудшение качества → оставить baseline.

| Уровень | floor(max(0, XP)/250)+1 |
| Сессия | +120 XP / +35 coins после допустимого локального финиша |
| Бонус входа | +10 coins, один раз в локальную дату |

Расчёт масштаба (не предложение изменить баланс): повышение одной группы до 5 стоит 25+50+75+100+125=375 coins, всех четырёх — 1500. Два дополнительных комплекта — 160. Не считать 48 тренировок предписанием по здоровью; это балансная модель. Перед расширением замерить распределение времени до покупки по сценариям игрока; не строить экономику на обязательных ежедневных нагрузках.

### 5.2 Предлагаемая модель контента (PROPOSED)

**Реестр предметов и наград:** typed definitions, immutable IDs, version. `ObjectiveDefinition {objectiveId, seasonVersion?, eligibility, requirements, rewardPolicyId, optional, expiresAt?}`; `ObjectiveProgress {objectiveId, qualifyingReceiptIds, state}`; `RewardGrant {rewardId, sourceType, sourceId, policyVersion, xpDelta, coinDelta, itemIds, grantedAt}`. Уникальность определяется типом выплаты и идентичностью source, а не только датой. Разрешённое сочетание base + tower + quest — различные предусмотренные политики, не «одна награда во всей системе». Повтор одного rewardId — no-op. Кошелёк изменяется только доменным переходом с атомарной записью и read-back; UI не вычисляет цену самостоятельно. Новые нормы/частичные цели — сначала ADR, migration, feature flag и отдельные тесты, существующие сохранения и право собственности неприкосновенны.

**Миссии:** единый видимый список на Горне: «Готова», «В процессе», «Получить», «Получена», «Недоступна» с понятной причиной. Новые задания из уже подтверждённых упражнений; учитывать eligibility (детектор валидирован, источник доверия). Три разновидности: освоение, разнообразие, добровольная долгосрочная цель. Отдых не отнимает XP и не обнуляет необратимый прогресс. Ввод шагов никогда не даёт экономическую награду. Отдельные задания на обучение/оформление могут давать косметические достижения, но не деньги за разрешения.

**Главы кампании:** сначала вертикальный срез одной законченной главы, затем остальные по data-driven контенту. Не создавать пять пустых карт ради количества.

| Глава | Смысл | Пример задач (после гейтов) | Награда-кандидат |
|---|---|---|---|
| I — Искра | создать героя, освоиться | калибровка, первая подтверждённая сессия, восстановление после отказа | эмблема новичка, короткая история |
| II — Уголь | устойчивый ритм | выбрать 2–3 доступные активности в удобные дни, опциональный отдых | вариант отделки формы |
| III — Молот | разнообразие | выбрать несколько валидированных движений, не требовать всех восьми | визуальная деталь мастерской |
| IV — Закалка | мастерство | персональная стабильность/повторяемость при хорошем кадре, не гонка скорости | цвет/рамка личной вехи |
| V — Сталь | собственное достижение | добровольный финальный набор и отражение истории | титул/косметика, открытый свободный режим |

Сюжет: кузница — метафора характера, а не «идеального тела». Короткие фрагменты повествования, авторские оригинальные символы, повторно доступная летопись. Без копирования IP. Сезоны после главы I: косметические темы, без платного усиления и FOMO. Пропущенная глава остаётся доступной.

**Башня 2.0:** сохранить пять существующих этажей и исторические результаты. Новая параллельная линия испытаний (не менять старые пороги без ADR): критерии полного движения, стабильности наблюдаемого кадра, добровольного окончания; доступный режим без гонки. Не поощрять выполнение через боль или попытки уложиться в жёсткое время ценой техники. Бот — заданное правило. Сложность — предложенная, не навязанная. Предпросмотр условий и наград; retry не выдаёт второй first-clear.

**Ghost 2.0:** собственный прошлый валидный результат, совместимые exercise/target/validatorVersion; показать разницу темпа без давления; отклонение от цели не должно отменять безопасно завершённую тренировку. Старые splits без новых полей — legacy, сохранить; при несовместимости — объяснение, без сравнения. Новые ghost-форматы только после migration QA.

**Программы тренировок и мастерство:** отдельный `RoutineDefinition` с шагами (exerciseId, target, rest, instructions, optional alternatives), пользователь выбирает короткий сеанс, может пропустить/остановить. Это новая схема, не механическое изменение `TARGET_REPS`. Нельзя добавить 10/40 reps в UI, пока сериализация, totals, rewards, ghost, quests и импорт предполагают 20. Сначала versioned WorkoutReceipt, потом альтернативные цели. Частичный результат можно хранить как личную практику без действующего базового reward; условия будущей награды согласовать отдельно. Никакого автоматического определения гипертрофии по повторениям.

### 5.3 Баланс и исследование мотивации

Симулятор (отдельный pure TS модуль): модели «нерегулярный», «обычный», «активный без обязательного максимума», отсутствие миссий, tower replay, покупка/экипировка, возвращение после 30 дней. Генерировать только синтетические события; фиксированный seed, неизменный baseline, таблица поступлений/расходов, распределение time-to-first-purchase, доля недоступных предметов, доля кошельков с отрицательным балансом (должна быть 0), проверка дубликатов (0). Влияние новой экономики оценивать по понятности и выбору, не по максимизации времени/нагрузки. Наблюдать добровольное возвращение (D1/D7/D30 при достаточном наблюдении), завершение выбранной цели и self-reported clarity, число отказов/жалоб на давление. Не обещать retention до данных. Малый UX-пилот до опционального контролируемого исследования, рандомизация по участникам, predeclared primary endpoint, одинаковые правила, доверительные интервалы и missingness. Без обязательной телеметрии и без скрытой передачи здоровья.

## 6. 3D-персонаж и производство художественных ресурсов

### 6.1 Исходная ситуация

E11: проект уже содержит rigged MakeHuman derivative, efficient GLB, fallback-цепочку и новые авторские детали глаз/волос/кожи. Отчёт ocular описывает малый дополнительный GLB и воспроизводимость; realism — локальные поля роста для тела/одежды и on-demand рендер. Это направление надо завершить, а не удалить. Не принимать названия файлов «realistic» за визуальную оценку. Не трогать параллельные правки Avatar3D/asset scripts до согласованного ownership.

### 6.2 Целевая система и pipeline

1. **Asset registry:** assetId, source URL, лицензия/автор, source SHA, генератор/версия Blender, export options, derived SHA, triangle/vertex count, rigId, materials/maps, fallback, quality tiers. Зафиксировать исходный GLB и все новые карты из dirty tree. Проверить лицензии не только модели, но и текстур/шрифтов/аудио. Новые файлы не перезаписывают исходник. Khronos glTF Validator [S14] + импорт в Blender + визуальный тест. Ошибки валидатора блокируют поставку ресурса; warnings разбирать, не просто игнорировать.
2. **Rig & morphology:** стабильные bone names, иерархия, bind matrices, inverse bind, unit scale, локальная ориентация. Уровни 0–5 — игровая деформация, не измеренная анатомия. Тело и одежда используют согласованные поля роста; нормали/тангенты корректно пересчитать. Обязательные тесты симметрии, ограничений, монотонности и невмешательства в лицо, пальцы, обувь.
3. **Cloth & accessories:** волосы/головные аксессуары к head bone; обувь к foot/toe rig; одежда — skinned weights/shared rig либо совместимые морфы. Не использовать screen-space. Проверка контакта, зазоров, пересечений, joint flexion; решить clipping asset-side, а не скрывать всё oversized мешем. Таблица mesh→bone/weights→offset→supported poses→QA screenshots.
4. **Материалы и свет:** PBR albedo/normal/roughness/metalness/ORM с правильными color spaces; глаза, кожа, ткань, металл визуально различимы. Согласовать тени, tone mapping, освещение key/fill/rim; портрет может иметь дополнительные детали только если измерен бюджет. Для кожи — правдоподобный, не медицинский вид; не обещать настоящую SSS, если используется приближение. Не добавлять postprocessing без доказанного эффекта.
5. **Характер и анимация:** нейтральный уверенный idle, вдох/выдох как художественное движение (не измеренный пульс/дыхание), поворот drag и кнопками, портрет/рост, короткая реакция на покупку и подтверждённую веху. Animation mixer останавливается при невидимости и reduce motion. В будущем — авторские тренерские демонстрации на риге, отдельные от live pose; движения одобрены профильным специалистом, не выдавать аватар как зеркало реального пользователя. Никакого захвата лица/видеозаписи ради внешности.
6. **Качество и память:** существующие economy/balanced + optional high после device QA. DPR clamp, on-demand, lazy, fallback SVG/процедурный герой; компрессия texture/mesh (KTX2/meshopt только после сравнительного spike и approval). Один владелец renderer/scene, shared asset reference tracking. Dispose geometry, material, texture, skeleton/render targets, listener и ImageBitmap только после последнего владельца; Three.js прямо указывает, что ресурсы не освобождаются автоматически [S2].

### 6.3 QA-матрица 3D

| Ось | Значения |
|---|---|
| Телосложение | lean/solid, 4 группы каждая 0/5 + выборка промежуточных, попарное покрытие комбинаций |
| Камера | front, 3/4, profile, rear, полный 360°, full/portrait, zoom/yaw кнопкой и жестом |
| Внешность | все доступные hairstyles/skin/hair/trim/visor, каждый комплект; отдельные граничные случаи |

Снимки paired before/after с одинаковым rig/ракурсом/светом/viewport/seed; автоматический тест geometry + ручная художественная оценка по заранее определённой шкале 1–5 (силуэт, посадка, лицо, материалы, свет, читаемость; 2 независимых оценщика и разногласия). Шкала — проектная оценка, не физическая истина. Блокирующий дефект — заметный отрыв, недопустимое пересечение, потеря внешности, черный экран без fallback, рост ресурсов без объяснения. Цель: 20 циклов mount/unmount/navigation, отсутствие нарастающих leaks после стабилизации; учесть legitimate shared renderer caches. Измерить время загрузки, draw calls, VRAM proxies и реальные frame times, батарею отдельно. Не менять триггер камеры ради 3D.

## 7. Данные, офлайн, Android, приватность и онлайн

### 7.1 Надёжность и перенос

**Не переписывать существующий journal.** E05 уже содержит ключевые механизмы. Сначала модель отказов: crash до stage, после stage, до/после profile write, до mark settled, quota, web lock unavailable, конфликт двух вкладок, clock rollback, corrupted primary/backup, orphan receipt, legacy с отсутствующим ledger. Выявить фактические gaps. Важно: UI-история ограничена 60, кошелёк и дедуп старых выплат живут дольше. Нельзя вычислить все монеты из обрезанной истории.

Предлагаемая schema v2: ProfileIdentity; Wallet и RewardGrant; WorkoutReceipt append-only; AvatarAppearance; UserPreferences; MissionProgress. Существующий формат читать через версионный адаптер, не менять `bodyforge:pilot:v1` произвольно. Индекс истории отдельно от ledger; миграция copy-on-write: read current → validate → staged copy → verify exact totals/ownership/ids → atomic activation under lock → read-back; old snapshot остаётся до безопасного завершения. Не выдавать recovery из пустого профиля за сохранение. При ambiguous ledger — quarantine/recovery, никаких повторных наград.

**Импорт:** существующий inspector остаётся первым фильтром. Файл с лимитом (не повышать 16 MiB без измерения), строгая схема, ограничения глубины/строк/массивов/чисел, защита от prototype pollution/несовпадения ID, проверка дубликатов, версия/совместимость; preview diff без записи (XP/coins/owned/appearance/workouts, конфликт/неполные данные). Сначала безопасный replace с явным подтверждением, локальный backup текущего профиля и проверенный rollback; merge независимых устройств — отдельный ADR. Пользовательский JSON не доверенный источник инструкций или серверной валюты. Не включать в export raw health data, camera frames или IDs; предусмотреть возможность удаления личных данных по отдельной явной операции.

### 7.2 Offline-first

Этап 1: inventory всех URL, модель/WASM, GLB, шрифты, динамические чанки. Перенос pinned модели/WASM на локальные статические ассеты только после проверки лицензий, bytes/hash, размер и официальной совместимости. Не скачивать новые ресурсы без разрешения. Опциональное скачивание offline pack с ясным размером и статусом; не обещать offline до полной проверенной загрузки.

Этап 2: service worker с версионным cache manifest, atomic readiness, hash/checks, no mixed versions, запрет cache приватных путей/здоровья, update prompt только когда нет активной сессии или pending save. Не принуждать `skipWaiting` посреди тренировки. Сохранения не хранятся в cache. Проверка: cold offline (ожидаемое объяснение), warm offline (поддерживаемый набор), сеть пропала при загрузке модели, quota/eviction, update interrupted, downgrade/rollback, два таба разных версий, cache clear без profile loss. Если Android WebView не поддерживает часть PWA API, пакет локальных ресурсов — независимый путь. Документация service worker [S10] подтверждает механизм, а не реализацию BODYFORGE.

### 7.3 Шаги и Android

Текущая реализация E09: `LiveStepsPanel.java`, `LiveStepPolicy.java`, `HealthStepsActivity.java`, `MainActivity.java`, `nativeSteps.ts`, `StepsBoard.tsx`. Сохранить нативное отображение значения (не передавать health data в JS). Источники: Health Connect дневной aggregate по локальной дате, запрос по входу и 60s; системный step detector — отдельный foreground-счёт сеанса. Два независимых показателя, не складывать. Ноль — только измеренное нулевое значение/новый сеанс, отсутствие источника — «—» плюс причина. Health Connect может писать пакетами примерно раз в минуту или медленнее для иных источников; `TYPE_STEP_DETECTOR` даёт события, latency зависит от устройства [S4–S6]. В Android 14+ встроенный подсчёт Health Connect дополнительно зависит от SDK Extension 20+, июньское изменение 2026 атрибуции не должно ломать aggregate без DataOrigin-фильтра. Не хардкодить SPN. Источники могут иметь иные условия; отдельная проверка capabilities.

**Текущий пользовательский запрос:** работать в открытом VS Code, не собирать новый APK без отдельного поручения. Изменения Java не видны через Vite/в уже установленном APK. Web fallback отображает ручной режим, не Health Connect. Для web/local QA не имитировать системные показания. Android source compile + policy tests при правке допустимы без APK; actual native visual QA только отдельным запуском/сборкой после согласования.

**Дальнейшие фазы:**
- H1: проверка разрешений независимо (`READ_STEPS`, `ACTIVITY_RECOGNITION`), sensor availability, null/error, тайм-аут, revocation, timezone/DST, late callbacks; start/stop listener при видимости и lifecycle. Убедиться, что `FLAG_SECURE` защищает значения и не ломает другие экраны; проверить размеры/крупный шрифт, multi-window, accessibility. Тестировать, что UI и камера не конкурируют; не логировать числа и не снимать защищённые экраны с реальными данными.
- H2: нормализовать visual parity, отделить native host и shared design tokens. Возможный typed capability contract только screen state/permission availability; передача реальных чисел через JS — новая privacy boundary, не разрешена автоматически. Сохранить отсутствие addJavascriptInterface для здоровья. Permission rationale, system revoke, no background/history/write permission. Никакого автоматического Health Connect → XP, sleep/heart/calories/GPS. iOS HealthKit/носимые устройства — отдельный spike только по необходимости и с permission review.
- H3: продуктовый Android-путь: выбрать package identity/signing/migration из тестового `healthqa`, стандартный build (Gradle/AAB при принятии решения), target SDK migration и field QA. На дату исследования официальное требование Google Play для новых обычных приложений/обновлений с 31.08.2026 — target API 36+ [S12]. Текущий target 34 не соответствует этому релизному пути. Это не запрет локального теста. Проверить актуальные исключения перед подачей, Android 15/16 behavior changes, 16 KB native page-size requirements при наличии нативных библиотек, Play Console Health permissions/Data safety и privacy policy [S15]. Не менять package ID/ключ без миграционного проекта, иначе Android может создать новый пустой профиль. Старый APK не перезаписывать. Production signing ключи не запрашивать в чате.

### 7.4 Безопасность и будущая сеть

Local-first — основа. Threat model: вредоносный backup, двойная выплата, race между вкладками, XSS/уязвимый WebView, избыточные разрешения, цепочка зависимостей, утечка private canon/public paths, spoofed records, перегрузка, unsafe URL navigation. OWASP MASVS [S16] — рамка требований, не результат сертификации. Тесты `qa:privacy`, asset allowlist, locked dependencies, SBOM, hash/лицензии, CSP после совместимого spike (WASM/worker), secure context `getUserMedia` [S11], least privilege. Никогда не отправлять raw video/landmarks, имя, health data, deviceId, private paths; диагностические метрики локально, сетевые только отдельный opt-in с минимизацией/retention. Учитывать, что даже preview URL публичен и может обращаться к реальному backend [S17].

**Online (не начинать до релизного качества solo):** сначала read-only асинхронные социальные функции на отдельной среде и opt-in; аккаунты необязательны для solo. ADR выбора backend (сравнить имеющуюся Firebase-инфраструктуру и альтернативы по цене/региону/авторизации/удалению данных; не использовать память Искры как игровую БД). Серверные права на записи, уникальные event IDs, авторизованный userId из token, транзакции, idempotency, rate limits, аудит, блокировка/жалоба, экспорт/удаление, age policy и модерация. Не доверять клиентским XP, времени, локальным save или Health Connect как anti-cheat. Сервер не может магически доказать движения без дополнительного доказательного протокола; без приватного безопасного решения рейтинги ограничить casual/noncompetitive. Последовательность: аккаунт/синхронизация косметики → асинхронные добровольные клубы/кооперативные цели → только после fraud review рейтинги и PvP. Никаких фальшивых игроков, рейтингов или чатов. Не добавлять монетизацию до отдельного решения; если нужна, косметика без pay-to-win, прозрачная цена и отмена, без азартных/штрафных циклов.

## 10. План работ и ресурсные ограничения

Не давать календарных обещаний без оценки реального доступного времени владельца, команды и устройств. Это несколько последовательных пакетов, не одна команда Codex. Предварительный порядок и оценочный диапазон трудоёмкости (инженерные рабочие дни, не срок исполнения):

| Пакет | Результат | Оценка до уточнения | Необходимые ресурсы |
|---|---|---|---|
| A. Stabilize | R0 и основные R1; чистая доказательная база | 3–10 дней | TS/QA, локальный Windows; время на конфликтующие правки |
| B. Reliable camera | R2, полевые протоколы и поддерживаемый subset | 15–40+ дней, поле отдельно | CV engineer, устройства, добровольцы, специалист по движению |
| C. Signature visual slice | R3/R4; согласованный герой и основной UX | 15–35+ дней | Blender/Three, art review, mobile QA |
| D. Deep solo RPG | R5 от первой главы к следующим | 10–30+ дней | game designer, content, тест экономики |
| E. Autonomy + Android | R6, безопасный перенос, offline, native parity | 10–25+ дней | Android QA, SDK, privacy review, разрешение на APK |
| F. Release | R7 и фиксированный кандидат | 5–15+ дней | release access, field evidence, rollback |
| G. Online | R8 только если обоснован | отдельная оценка после ADR | backend/security, moderation, бюджет и правовая экспертиза |

Это грубые planning ranges, не сумма гарантированного времени и не обещание календаря. Могут увеличиться из-за rig/полевых данных/устройств и migration. Один разработчик выполняет последовательно; внешние эксперты требуются для надёжного движения/художественной оценки/публикации. Не экономить на исследованиях за счёт риска пользователя. Владелец может отложить расширенный контент и online, чтобы раньше получить качественный solo release. Дополнительные возможности не должны удерживать готовый безопасный core в вечном переписывании.

**Приоритет задач:** P0 — риск данных, наград, приватности, камеры, невозможность основного сценария; P1 — достоверность, доступность, UX/визуальное качество, производительность, восстановление; P2 — контент; P3 — внешняя инфраструктура/расширения. Для сопоставимых задач записать impact (1–5), observed frequency (UNKNOWN до данных), reproducibility, dependency criticality, reversibility и cost. Отсутствующие показатели не заполнять числами. Сначала строгий safety gate, затем high-confidence пользовательский эффект с минимальным обратимым diff. Не умножать «субъективные 5» и выдавать за научный рейтинг.

## 11. Инженерный протокол: QA, приёмка и выпуск

### 11.1 Один технический цикл

1. **INTAKE:** проверенная боль, ID backlog, user-visible result, актуальный HEAD/status и точные файлы. Если текущий файл уже изменён, прочитать/сравнить; сохранить чужую работу. Разрешение локальной правки не равно разрешению внешней публикации.
2. **SIFT / CONTRACT:** указать исходник/секцию/лог, разделить факт и гипотезу, записать отрицательный тест. Если базовый сценарий уже PASS, не исправлять несуществующий дефект; уточнить цель или выбрать следующий.
3. **PLAN:** 1–3 production файла как обычный ориентир; отдельные тесты. Один инвариант, минимальный diff, rollback, команды и safe assumptions. Большая задача разбивается на микропатчи; tests fail on old code for actual bug. Не создавать новый репозиторий или скрытый клон вместо открытого проекта.
4. **PATCH:** strict TypeScript, pure domain rules, runtime validation, cancellation, ownership, доступность. Не изменять правила теста ради зелёного результата; обновление селектора при реальном UX изменении должно сопровождаться проверкой нового поведения и сохранённого инварианта.
5. **VERIFY:** focused unit/negative tests → полный unit → production build → отдельный стабильный preview exact entry HTTP 200 + actual DOM + no exception → профильный E2E → `git diff --check` → read-back файлов/сохранений. Тестовые профили изолированы от пользовательских. Не останавливать пользовательский dev server. Для реального телефона отдельный consent/surface gate.
6. **RECEIPT:** `docs/audits/BF_<ID>_<date>/RECEIPT.md`, before/after hashes, path, bytes, actual commands/exit, tests count, environment, synthetic/field distinction, screenshots if relevant, untested, rollback and next task. Не включать личные данные, secrets или приватный canon в публичный repo; проверять статус/ignore. Нативный APK только после разрешения. Запись receipt подтверждается чтением.
7. **STOP/NEXT:** PASS → следующий минимальный инвариант; FAIL → диагностика и ограниченная коррекция/rollback только своего патча; BLOCKED → конкретное отсутствующее условие. Не делать скрытые retries. Не обещать выполнение в фоне. Если guard/permission запрещает действие, планирование остаётся допустимым.

## 12. Риски, альтернативы и ADR-реестр

| Риск / изменяемая предпосылка | Ранний тест | Контроль / остановка |
|---|---|---|
| Параллельные изменения совпали по файлам | status + per-file SHA до/после | stop write, согласовать ownership; не откатывать чужой файл. |
| Detector false positives/coverage low | negative replay + holdout по упражнению | ограничить mode/angle, оставить experimental; не упростить порог ради PASS. |
| Награда повторена после crash | stage/write/settle fault injection | disable new reward policy, recovery, сохранить журнал. |

| Детали героя слишком дороги для GPU | paired device trace, asset inventory | economy/fallback, отказаться от high tier; не жертвовать CV. |
| Offline cached version несовместима | mixed version / interrupted update | atomic activation, block update mid-workout, preserve storage. |
| Health read отсутствует или задержан | deny/revoke, no sensor, clock, permission lifecycle | «—»/source lag, не арифметическое слияние и не fake numbers. |

| Online увеличил exposure/cheating | cross-user tests, threat model, replay | remain local/casual until evidence; no unapproved data upload. |

| Нет физического телефона или добровольцев | device inventory and consent | field BLOCKED, synthetic PASS не заменяет. |

- Базовая: текущая архитектура выдерживает field requirements → эволюция по малым шагам. Дискриминатор: measured device/CV/reward gates.
